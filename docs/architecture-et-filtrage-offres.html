Architecture de Gesta et parcours d'affichage des offres

Ce document décrit l'organisation actuelle du projet Gesta, puis suit une offre de stage depuis le composant React jusqu'à SQLite. Il identifie enfin les fichiers qui seraient probablement concernés par l'ajout d'un filtre par période (P1, P2 ou Autre).

1. Vue d'ensemble

Gesta est un monorepo npm composé de deux workspaces. Le frontend est une application React/TypeScript construite avec Vite. Le backend est une API Node.js/Express écrite en TypeScript. Les deux communiquent avec une base SQLite locale utilisée via better-sqlite3.

Partie Technologies Dossier principal Responsabilité
Frontend React, TypeScript, Vite, React Router frontend/ Rendu de l'interface, navigation, état de session et appels HTTP.
Backend Node.js, Express, TypeScript backend/ API, authentification, autorisation et règles métier.
Persistance SQLite, better-sqlite3, migrations SQL backend/data/ et backend/src/db/ Stockage des entreprises, offres, périodes, utilisateurs et stages.

Le démarrage global est défini dans package.json :

npm run dev
  ├── backend  : API sur http://localhost:3000
  └── frontend : application sur http://localhost:5173

2. Couches du backend

Le backend suit une séparation en couches. La composition et l'injection des dépendances sont réalisées dans backend/src/app.ts, tandis que le démarrage et l'initialisation de la base sont réalisés dans backend/src/main.ts.

Couche Fichiers représentatifs Rôle
Entrée et composition backend/src/main.ts, backend/src/app.ts Charge la configuration, initialise SQLite, crée les services et branche les routes.
Controllers backend/src/controllers/offers.controller.ts Expose les routes HTTP et transforme le résultat en réponse JSON.
Middlewares backend/src/middlewares/authenticate.ts, authorize.ts, errorHandler.ts Identifie l'utilisateur, contrôle les droits et uniformise les erreurs.
Services métier backend/src/services/offers.service.ts, services/permissions.ts Décide quelles offres sont visibles selon le profil.
Repositories backend/src/repositories/offers.repository.ts Exécute les requêtes SQL paramétrées et renvoie des DBO.
Models et mappers backend/src/models/offer.ts, backend/src/mappers/offer.mapper.ts Décrit les types et convertit les lignes SQL en objets métier puis en DTO.
Base de données backend/src/db/database.ts, db/initialize.ts, db/migrations/001_initial.sql Ouvre SQLite, applique les migrations et définit le schéma.

4. Parcours d'affichage d'une offre

OfferTable.tsx affiche le tableau OffersPage.tsx utilise useOffers useOffers.ts appelle getOffers offers.service.ts envoie GET /api/offers vite.config.ts redirige vers GET /offers authenticate.ts identifie l'utilisateur authorize(canListOffers) vérifie l'accès offers.controller.ts appelle le service offers.service.ts construit le filtre métier offers.repository.ts exécute la requête SQL SQLite lit offers, companies, academic_years et periods

4.1 Depuis React jusqu'à l'appel HTTP

  1. App.tsx rend OffersPage si l'utilisateur est autorisé par frontend/src/utils/permissions.ts.
  2. OffersPage.tsx transmet le token et la fonction onUnauthorized à useOffers.
  3. useOffers.ts lance l'appel dans un useEffect, gère le chargement, les erreurs et l'annulation via AbortController.
  4. offers.service.ts appelle /api/offers avec le token dans l'en-tête Authorization.
  5. frontend/vite.config.ts supprime le préfixe /api et transmet la requête au backend sur le port 3000.

4.2 Authentification et autorisation côté serveur

Le middleware authenticate.ts vérifie le token puis recharge l'utilisateur, ses rôles et ses rattachements en base. Le token ne constitue donc pas la source complète des permissions.

Ensuite, authorize(canListOffers), dans backend/src/controllers/offers.controller.ts, autorise uniquement :

  • les administrateurs ;
  • les étudiants ;
  • les contacts qui possèdent le rôle DEPOSITOR.

Un utilisateur non authentifié reçoit 401. Un contact sans droit de consultation reçoit 403.

4.3 Lecture dans SQLite

offers.service.ts transmet un OfferFilter au repository. Celui-ci exécute une requête paramétrée dans backend/src/repositories/offers.repository.ts. 

SELECT o.id, o.title, o.description, o.status,
       o.company_id, c.short_name AS company_short_name,
       o.depositor_contact_id,
       ay.label AS academic_year_label, p.code AS period_code,
       o.created_at, o.updated_at
FROM offers o
JOIN companies c ON c.id = o.company_id
JOIN academic_years ay ON ay.id = o.academic_year_id
JOIN periods p ON p.id = o.period_id
WHERE (@status IS NULL OR o.status = @status)
  AND (@depositorContactId IS NULL
       OR o.depositor_contact_id = @depositorContactId)
ORDER BY ay.start_date DESC, o.created_at DESC

Le schéma et les contraintes sont définis dans backend/src/db/migrations/001_initial.sql. La table offers référence l'entreprise, l'année académique et la période.

4.4 Retour vers l'interface

  1. Le repository renvoie des OfferDbo avec des noms proches du SQL, comme company_id et period_code.
  2. offer.mapper.ts convertit ces données en objet métier puis en OfferDto.
  3. Le DTO de liste contient notamment id, title, companyShortName, academicYear, period et status.
  4. Le frontend valide le JSON avec isOfferList, puis OffersPage.tsx transmet la liste à OfferTable.tsx.
  5. labels.ts convertit les codes comme PUBLISHED et P1 en libellés français. StatusBadge.tsx affiche le statut.

5. Filtrage actuel selon le profil

Profil Accès à GET /offers Filtre envoyé au repository Résultat attendu
Administrateur Oui {} Toutes les offres et tous les statuts.
Étudiant Oui { status: "PUBLISHED" } Uniquement les offres publiées.
Contact déposant Oui { depositorContactId: viewer.id } Les offres déposées par ce contact, quel que soit leur statut.
Contact sans rôle déposant Non Aucun appel métier autorisé Réponse HTTP 403.

Le frontend masque la route et le lien de navigation pour les profils non autorisés, mais le backend reste l'autorité de sécurité. Un appel direct à l'API ne permet donc pas de contourner le filtre métier.

6. Ajout futur d'un filtre par période

La période est déjà présente dans le modèle et la base : le code est stocké dans la table periods avec les valeurs P1, P2 et OTHER. L'ajout d'un filtre nécessite donc surtout de faire circuler une valeur optionnelle depuis l'interface jusqu'au repository.

6.1 Fichiers probablement à modifier

  • frontend/src/pages/OffersPage.tsx : ajouter l'état du filtre et un contrôle de sélection (P1, P2, Autre), puis le transmettre au hook.
  • frontend/src/hooks/useOffers.ts : accepter la période comme paramètre, relancer le chargement lorsqu'elle change et la transmettre au service.
  • frontend/src/services/offers.service.ts : encoder la période en paramètre de requête, par exemple /api/offers?period=P1.
  • frontend/src/models/offer.ts : réutiliser PeriodCode pour typer la valeur du filtre, sans nécessairement modifier le modèle d'offre.
  • frontend/src/utils/guards.ts : vérifier que le filtre reçu ou choisi fait partie des codes autorisés si une validation supplémentaire est nécessaire.
  • frontend/src/utils/labels.ts : réutiliser ou compléter le libellé français de OTHER avec « Autre » pour le contrôle et l'affichage.
  • backend/src/controllers/offers.controller.ts : lire et valider req.query.period, puis le transmettre au service.
  • backend/src/services/offers.service.ts : combiner le filtre de période avec le filtre actuel du profil sans supprimer les règles de visibilité.
  • backend/src/repositories/offers.repository.ts : ajouter periodCode au type OfferFilter et une condition SQL sur p.code ou o.period_id.
  • backend/src/repositories/offers.repository.ts : le repository est l'endroit naturel pour appliquer le filtre puisque la requête joint déjà periods.

6.2 Fichiers probablement inchangés

  • backend/src/models/offer.ts possède déjà PeriodCode = "P1" | "P2" | "OTHER".
  • backend/src/db/migrations/001_initial.sql définit déjà les codes autorisés par la contrainte de la table periods.
  • frontend/src/components/OfferTable.tsx affiche déjà la période ; il ne devrait pas être nécessaire de le modifier pour filtrer la liste.
  • backend/src/mappers/offer.mapper.ts transmet déjà period_code vers le DTO.

6.3 Forme probable du filtre

Le filtre devrait rester optionnel afin de préserver le comportement actuel lorsque aucune période n'est sélectionnée : 

GET /offers
GET /offers?period=P1
GET /offers?period=P2
GET /offers?period=OTHER

Au niveau du repository, la condition pourrait suivre le même principe que les filtres existants : 

AND (@periodCode IS NULL OR p.code = @periodCode)

Le filtre de période doit être combiné avec le filtre de profil. Par exemple, un étudiant demandant P1 doit obtenir uniquement les offres PUBLISHED de la période P1, et un déposant demandant P2 doit obtenir uniquement ses propres offres de cette période.

7. Tests concernés par cette évolution

Pour préserver le comportement existant, les tests devraient être étendus aux deux côtés de l'application :

  • backend/tests/offers.test.ts : vérifier P1, P2 et OTHER pour les différents profils, ainsi que l'absence de filtre.
  • frontend/tests/OffersPage.test.tsx : vérifier l'affichage du contrôle, la requête avec le paramètre choisi et les états de chargement ou d'erreur.
  • frontend/tests/NavBar.test.tsx : conserver la visibilité de la route selon le profil.
